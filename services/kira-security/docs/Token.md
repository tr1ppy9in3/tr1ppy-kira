# Архитектура управления сессиями 

Данный документ описывает процессы аутентификации, генерации, обновления и отзыва токенов в микросервисе `Kira.Security`. Система построена с использованием паттернов **Stateless JWT**, **Refresh Token Rotation**, **Token Binding** и **Blacklisting**, что обеспечивает высокий уровень безопасности корпоративного класса (Enterprise-grade security).

## 1. Концепция гибридных сессий

Система использует два типа токенов для обеспечения баланса между производительностью микросервисов и управляемостью сессиями:

1. **Access Token (JWT):**
    - **Тип:** Stateless (не хранится на сервере).
    - **Назначение:** Используется для межсервисной авторизации (содержит `UserId`, `Roles`).
    - **Время жизни:** Короткое (15-60 минут).
    - **Производительность:** Микросервисы валидируют его криптографическую подпись локально, без сетевых издержек.

2. **Refresh Token (Opaque Token):**
    - **Тип:** Stateful (хранится в распределенном кэше Redis).
    - **Назначение:** Используется исключительно для запроса новой пары токенов (Access + Refresh).
    - **Время жизни:** Длительное (дни/недели).
    - **Криптография:** Представляет собой 256-битное случайное значение, сгенерированное через криптографически стойкий генератор псевдослучайных чисел (`RandomNumberGenerator`).

---

## 2. Механизм привязки токенов (Token Binding)

Для защиты от атак типа *Token Substitution* (использование украденного Refresh Token в отрыве от сессии) реализован механизм жесткой криптографической связки (Binding).

### Логика связки:
1. При генерации Access Token в него добавляется уникальный идентификатор `jti` (JWT ID).
2. При сохранении Refresh Token в Redis, в объекте сессии фиксируется поле `AccessTokenId`, равное сгенерированному `jti`.
3. При попытке обновления сессии (Refresh), сервер извлекает `jti` из предоставленного клиентом (даже просроченного) Access Token и сверяет его со значением в Redis.

**Детекция компрометации:**
Если значения `jti` не совпадают, система классифицирует это как попытку несанкционированного доступа (угон сессии). В этом случае срабатывает алгоритм **Global Sign-Out** — сервер немедленно удаляет из Redis все активные сессии данного пользователя.

---

## 3. Ротация токенов (Refresh Token Rotation)

Система реализует строгую политику одноразового использования (One-Time Use) для Refresh токенов.

### Жизненный цикл (Flow):
1. Клиент отправляет POST-запрос с просроченным `Access Token` (в заголовке) и актуальным `Refresh Token`.
2. Сервер валидирует связку токенов (Token Binding).
3. **Ротация:** Сервер удаляет использованный `Refresh Token` из Redis.
4. Сервер генерирует новую пару (новый Access + новый Refresh) и связывает их новым `jti`.
5. Новая сессия сохраняется в Redis.

*Такой подход гарантирует, что в случае перехвата Refresh токена злоумышленником, он сможет использовать его лишь однажды, после чего легитимный пользователь получит ошибку при попытке обновления и выявит факт кражи.*

---

## 4. Мгновенный отзыв доступа (Token Blacklisting)

Фундаментальным недостатком классических JWT является невозможность их отзыва до истечения срока действия (`exp`). Для решения этой проблемы в `Kira.Security` внедрен механизм **Черного списка (Blacklist)**.

### Алгоритм работы:
1. **При выходе из системы (Logout):**
    - Refresh Token удаляется из Redis.
    - Текущий (активный) Access Token заносится в специальный список в Redis (`blacklist:{token_hash}`).
2. **Время жизни в кэше:** TTL (Time-To-Live) записи в черном списке устанавливается равным остаточному времени жизни самого Access Token. Это предотвращает бесконечное разрастание базы Redis.
3. **Проверка (Middleware):**
    - Слой `TokenBlacklistMiddleware` (или API Gateway) проверяет каждый входящий запрос.
    - Благодаря использованию двухуровневого кэша `FusionCache` (L1 Memory + L2 Redis), проверка наличия токена в черном списке выполняется за доли миллисекунды, не создавая "бутылочного горлышка" (bottleneck).

---

## 5. Вторичное индексирование (Secondary Indexing)

Поскольку Redis является Key-Value хранилищем, поиск всех сессий пользователя для принудительного разлогина (команда `RemoveAllUserTokensAsync`) мог бы стать ресурсоемкой операцией.

Для решения этой проблемы применен паттерн **Вторичного индексирования**:
- Основные ключи: `refresh_token:{token}` -> `[SessionData]`
- Индекс: `user_sessions:{userId}` -> `Set[ token_1, token_2, ... ]`

При создании сессии токен добавляется в обе структуры. При отзыве доступа система за $O(1)$ получает список всех токенов пользователя из индекса и удаляет их из основного кэша, обеспечивая высокую масштабируемость БД.

---

### Заключение
Реализованная архитектура обеспечивает высокую производительность микросервисного взаимодействия за счет делегирования авторизации (Stateless JWT), сохраняя при этом централизованный контроль (Stateful Sessions), возможность мгновенного реагирования на инциденты информационной безопасности и защиту от повторного использования токенов.
